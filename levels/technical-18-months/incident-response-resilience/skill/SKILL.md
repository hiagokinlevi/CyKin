## First-five-chapter lab checkpoints

Teach the new worked replays only after the learner predicts a result. Keep each as a separately labeled fictional branch, then return to the numbered exercises and their appendix answers.
1. In Chapter 1, request a service outcome contract and a three-column L1-V worksheet. Ask why a static 200, a database read and an old backup cannot establish a successful reservation write. Keep graph variant G2 distinct from card V2.
2. In Chapter 2, compare H-path and H-processing before releasing N2-V A or B. Require the exact source-coverage premise; remove it as a negative control and weaken any claim of universal absence.
3. In Chapter 3, inspect a five-column join ledger. A producer-validated session-to-request mapping in hypothetical L3-V can strengthen one edge but does not identify H01 as the actor or settle human attribution.
4. In Chapter 4, use L4-Q to separate logical record ordinal 4 from physical line 5. Require two accepted IDs, one duplicate rejection, and a duplicate-header fail-closed control; never import L4-Q into the main incident.
5. In Chapter 5, compare the 43-byte LF original with its 45-byte CRLF variant. Separate scope, acquisition, transformation and interpretation; matching hashes of classroom bytes do not authenticate a production exporter.

## Chapter 6 route-contract checkpoint

1. Ask for the four original L6 dependency sets before discussing cache or database fallbacks. Keep `cached_room_read = {edge, api}` intact; cache eligibility is a runtime precondition, and the database fallback is an explicitly declared variant. The five-minute cache lifetime is fictional and does not establish a business freshness target.
2. Have the learner build a route contract for each function: components, preconditions, observable result, business correctness, evidence source, validation owner and falsifier. Contrast declared configuration, deployed configuration, exercised path, producer observation and validated outcome. A response code or cache-hit log alone cannot establish an authorized, current room list or durable reservation.
3. In the [§6.1 offline lab](../en/book/MANUSCRIPT.md#ch-06), predict the seven scenario lines before running the Python code. Verify the exact transcript, then ask why `ACK_WITHOUT_COMMIT` returns `FAIL(201)` and why `CACHE_SEMANTICALLY_STALE` returns `FAIL(200,cache)`. Both failures concern the modeled business acceptance criterion despite an apparent HTTP success. The simulator does not implement a real HTTP server, IdP, database or backup.
4. For EX021, keep records L6-E21-A–E separate from N01–N06. Require the four-route matrix, an evidence classification, IdP impact analysis, the 240-second versus 300/120-second freshness comparison, a bounded write-verification request and a limited final assessment. Use its 12-point diagnostic rubric and convert it to the book's 0–2 scale as directed in the exercise. Consult the worked answer only after a learner submits the artifacts.
5. Move to §6.2's simpler dependency-set model after §6.1: it isolates *which routes list a failed component*, whereas §6.1 tests runtime preconditions and business acceptance. Then use §§6.3–6.4 for control approval, rollback and restore-point checks. Neither model is production evidence or authority for a live change.

## Technical tutoring cycle

1. Ask the learner to state the component, observation, producer and decision question before presenting any command or code. Use only the literal offline fixtures in the manuscript; `.test` names and TEST-NET addresses are examples, not live targets.
2. Have the learner predict each fixture's exact output, run it in a local Python 3 interpreter if desired, and compare the output with the worked result. The code checks a model, not a production system. Ask what changing one input does and why the variant does not rewrite the original record.
3. Require an evidence/request artifact and a negative or business-function check. For Chapter 1 distinguish graph closure from measured impact; for Chapter 2 distinguish client-to-edge from edge-to-API; for Chapter 3 do not join `sid-88` to `r-202` from a shared principal label.
4. In Chapters 4–8, ask which literal inputs are separate L4–L8 branches. Require a rejection report, an authority-and-provenance receipt, a route-level negative test, a retention anchor and a clock-uncertainty note before interpreting any output. Never merge a branch row into N01–N06 or infer a cause from one code or timestamp.
5. In Chapters 9–13, follow the K workshop in sequence: bounded collection, a control contract, corrected time, raw/derived manifest and alert predicates. In Chapters 14–18, demand a deterministic review packet, literal-versus-validated timeline, stop-state runbook, security and service gate, then a staged C18-A–D dossier. Do not release a later C18 card to justify an earlier version; do not import K rows into the main case.
6. Score EX001–EX072 against their 0–2 rubrics; show the [worked results](../en/book/MANUSCRIPT.md#worked-results) after each attempt. For open work, accept different conclusions when evidence, falsifier, owner and scope are explicit. Require a peer to challenge the final handoff's provenance and safety gates. Use the [chapter-end navigation](../en/book/MANUSCRIPT.md#ch-01) to move forward or back.

## Evidence and editorial boundaries

LLR is fictional and separate from CTN. No primary source is evidence for an LLR event. Documentation names and addresses are fixtures. A TLS handshake is not application authorization, a sampled missing row is not proof of no request, and a shared service principal is not a human. L4–L8 and K9–K18 are separate workshop inputs, not main-case releases. K15 D15 and K18 C18-A–D are staged additions; C18-C cannot be backdated into K12. Transport bytes do not prove application success; a toy rule or derived digest is not deployment or source-authentication evidence; rejected rows remain visible. Literal session matches, sorted clocks and a queued event do not prove causation or a DB commit. The isolated restore is a lab result, not a production recovery. Eighteen draft chapters and 72 worked exercises remain short of the 300-page A4 and review gate.
